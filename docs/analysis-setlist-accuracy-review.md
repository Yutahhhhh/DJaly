# 楽曲解析・セットリスト精度の点検と改善

2026-09-06。対象は現行バックエンドの解析、保存、候補検索、セットリスト生成、MCPの呼び出し経路。
今回はコードの不具合修正と回帰検証まで実施した。実ライブラリの正解率・試聴での採用率は未測定であり、精度向上率を数値で主張できる段階ではない。

追記（同日、v0.4.1）：以下は初回点検時点の記録。以後、選択解析・永続ジョブ・新旧埋め込みの比較分離を実装し、MCPのエラー文言テストも修正した。配布用環境の全187テストが通過し、ローカルアプリを更新して実ライブラリの移行を開始している。最新の操作・仕様は[選択解析と大量ライブラリの更新](selective-audio-analysis.md)を参照。

## 今回修正した問題

| 問題と確認した挙動 | 改善内容 | 対象 |
| --- | --- | --- |
| 44.1kHzで読み込んだ音声を、16kHzを前提とするMusiCNNへそのまま渡していた | 特徴抽出用区間を16kHzへリサンプリング。解析条件のバージョンと入力レートを保存 | `domain/services/analysis/analyzer.py`, `constants.py` |
| BPMを0.5刻みへ丸め、127.87を128.0にしていた | 保存精度を小数点以下2桁へ変更。これは表示・保存の量子化誤差の修正であり、検出器自体の正解率改善とは区別する | `analysis/analyzer.py` |
| 再解析時、brightness/noisiness/loudness/contrast/duration等が更新されず、energy等の正当な0値も反映されなかった | 結果に存在する有限の数値を更新。メタデータのみの更新では未指定の特徴量を保持。埋め込みモデル名も保存 | `infra/repositories/ingestion_repository.py` |
| `Db minor`、`Gb minor`、`Ab minor`を部分一致で全てB Minor＝10Aと誤認。`8a`を認識せず、無効な`13B`を受理 | キー全体を解析し、異名同音・短縮形・大小文字・♯/♭を扱う。Camelotは1〜12のA/Bのみ有効 | `utils/audio_math.py` |
| 不明BPMを120に置き換え、他の条件が一致すると満点。75→135と135→75のスコアも0.25と約0.383で非対称 | 不明BPMへの加点をなくし、対数比による対称な距離へ変更。半分／倍のテンポ解釈は維持 | `utils/audio_math.py` |
| スコアでは倍／半分を許しても、候補検索が先に70↔140等を除外。BPMだけの指定では新しい登録順の200〜400曲で候補を打ち切っていた | 候補検索も同じテンポ解釈に統一。BPM・指定特徴量への距離で並べてから件数を制限 | `infra/repositories/recommendation_repository.py` |
| 年代条件をサービス側で受理しても候補検索に未適用。brightness/noisinessも候補の順位に未反映 | 年代を両端含む必須条件にし、指定時は年不明を除外。明るさ・ノイズ量を候補順位へ反映 | 同上 |
| シード曲がSQL取得順になり、指定順を失っていた。先頭曲は上位10曲から無作為に選ばれ、再現性がなかった | シード順を保持して重複を除去し、曲数上限を守る。開始曲と同点時の選択を決定的にする | `setlist_app_service.py`, `setlist_builder.py` |

MusiCNNの入力条件は[Essentia公式リファレンス](https://essentia.upf.edu/reference/std_TensorflowPredictMusiCNN.html)と、インストール済みライブラリの説明で確認した。

MCPの`generate_auto_setlist`と`recommend_next_track`にも、`year_min`、`year_max`、`target_noisiness`を追加した。例：

```json
{
  "length": 10,
  "genres": ["Hip-Hop"],
  "year_min": 1990,
  "year_max": 1999,
  "target_bpm": 94,
  "target_energy": 0.6
}
```

ジャンル文字列はライブラリ内の実際の表記に合わせる。シード曲は明示した曲として優先し、年代・ジャンル条件は追加候補に適用する。候補不足なら条件を勝手に緩めず、指定曲数より短い結果になる。`min_length`/`max_length`による曲数のランダム選択は従来どおり。

| P2 | 最大音量の60秒だけを埋め込みへ使う。イントロ／アウトロや展開を捉えにくい | 冒頭・中盤・終盤の複数区間と現方式を、同じ計算時間枠で比較。全体の類似性と実際のミックス区間の相性を別々に評価する |
| P2 | energy等は固定範囲の正規化。マスタリング音量を盛り上がりと混同する可能性 | ジャンル別の分布・0/1への飽和率を確認。音量、ビート密度、帯域構成等を別特徴として検証。ライブラリ変更のたびに値が変わる無版管理の正規化は避ける |

## 既存曲へ反映する際の注意

今回、実ライブラリの一括再解析や音源タグの書き換えは実行していない。
通常のインポートは「埋め込みあり・メタデータ変化なし」の曲をスキップするため、アプリを更新しただけでは既存の埋め込みは修復されない。

次の実データ評価は、バックアップしたDBと代表曲の集合で行う。現状のforce_update経路は音響特徴以外にファイル由来のジャンル等も保存し、隣接LRCがあれば音源への歌詞書き込みも実行する。そのため、本番ライブラリへの展開前に「特徴量だけ更新して手確認済みタグを維持する」再解析経路を整える必要がある。
前処理バージョンがないデータは「旧／条件不明」であり、個々の曲が必ず誤って解析されたと断定するものではない。

## 検証

- 最終の関連テスト74件は全て通過。全体実行では下記のMCPエラー文言テスト1件が失敗した。MCPテスト終了時にSSE監視タスクの未終了ログ、設定クラスにはPydanticの非推奨警告も出る。
- `backend/tests/test_accuracy.py`：キー表記、テンポ対称性、不明BPM、リサンプリング、BPM保存精度、特徴量再保存、年代条件、候補打切り前の順位、シード順、再現性を検証。
- リサンプリングの回帰テストは実際のEssentia Resampleを使用。4秒・440Hzの音声が64,000サンプルとなり、440Hzを維持することを確認。推論部分のみモック。
- 別途、同梱の`msd-musicnn-1.pb`で実推論。176,400→64,000サンプルへの変換後、`(1, 200)`の有限値ベクトルを確認。これは実行可能性の確認であり、音楽的な精度評価ではない。
- MCPの年代指定は実MCPクライアントからの呼び出しで検証。
- 全体テストで残った`test_update_track_genre_not_found`は、存在しない曲へのエラー本文に`not found`を期待するが、インストールしたMCP 2.1.1では`Error executing tool update_track_genre`となる。今回の精度変更とは別のエラー表現の互換性課題として残す。

再実行例（本番DBを参照しない）：

```sh
DB_PATH=/private/tmp/djaly-accuracy-tests.duckdb USER_DATA_DIR=/private/tmp/djaly-accuracy-tests backend/venv/bin/python -m pytest backend/tests -q --tb=short
```

検証環境：既存の`backend/venv`（Python 3.11、Essentia TensorFlow 2.1b6.dev1389）へ不足していたテスト依存等を追加。MCP 2.1.1、cryptography 48.0.1を使用。macOS x86_64用のcryptography最新版をソースビルドできなかったため、検証環境では配布済みバイナリを利用した。プロジェクトの依存定義自体は変更していない。
