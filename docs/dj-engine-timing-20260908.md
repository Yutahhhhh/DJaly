# DJエンジンの再生タイミング調査・修正（2026-09-08）

## 原因の切り分け

フロントを通さず、CoreAudio / BlackHole 2chで実際のホストにJSONコマンドを送り、位置と録音PCMを測定した。

| 経路 | 修正前の確認結果 | 対応 |
| --- | --- | --- |
| 解放時の制動 | 20ms位置トレースで解放後の停止区間を再現。コールバック計測でも速度ゼロ付近への減速が残った | `braking_`、300ms待ち予算を撤去 |
| 着地シーク | 600ms / 150msの逆方向ドラッグで、500msの位置ジャンプを検出。20ms外部トレースでも約479msの逆方向ジャンプ | `Host::landScratch`と着地待ち状態を撤去 |
| Mixxx quantize | 初期状態がON。着地シークに拍合わせが作用。`SyncControl::requestSync`の位相シークに加え、`BpmControl::calcSyncedRate`にも継続的な位相補正がある | Mixxx COを初期化時にOFFにし、その後は変更しない |
| 停止中のquantize切替・キュー登録 | 既存の位置据え置き対策では1360msを保持できた。ただし切替後の補償シークとCOの一時切替に依存 | 配置用設定と拍丸めをホスト側へ分離。補償シークを撤去 |
| 位置通知 | 定常再生でも20msポーリングからの差分速度は0〜2倍以上に揺れた。これは音声速度の測定には使えない | オーディオコールバック単位の独立トレースを追加 |
| フロント・プリロール | ネイティブホスト単独、曲の5〜10秒地点で再現したため、今回の停止・着地ジャンプにフロントやプリロールは必要ない | 正時間のスクラッチはシークを送らず、endを送る既存経路を維持 |

`getExactPlayPos()`は`EngineDeck::process()`直後にはまだ更新されていない。全デッキ処理後の`postProcess()`で更新されるため、計測はその直後で行う。通知上の`rate`はテンポ設定比率であり、スクラッチ中の実速度ではない。実速度はソースフレーム差分と音声バッファ長から算出する。

旧版コールバック証拠: `/var/folders/39/w3nmjg1566q3djxm89qhhvhc0000gn/T/djaly-timing-qc6xc4/evidence.json`。当初の復帰判定は46.4msだったが、その後にも着地シークがあるため、この数値を「安定復帰完了」とは扱わない。500msジャンプは位置トレースで直接確認している。旧版の437.3Hz PCM比較は行っていない（旧版録音は440Hzで、500msの移動を同一位相に隠し得る）。

## スクラッチの設計

`scratch_position`の16msサンプリング、PIDの追従遅れ、40ms停止判定、throw慣性を使わず、`scratch2`で各音声バッファのレートを指定する。

1. 掴んだ時点の実位置を音声スレッドで保持する。目標はその位置＋相対ソース位置。
2. ドラッグ中は位置誤差を2バッファのソースフレーム数で割ってレートにする。上限は±16倍。Mixxxの線形リサンプラーがバッファ内でレートを補間する。最後の位置変更から30ms経過したら追従ゲインを半減し、方向反転の履歴を持つリサンプラーに対して固定目標への追従を減衰させる。
3. 解放時は最終目標までの残差と通常速度を使い、最後の補正バッファのレートを計算する。その次のバッファで通常速度へ補間する。逆方向への切替ではMixxxが半バッファずつ補間する点も計算に含める。再生中の中間レートは絶対値0.25以上にする。ほぼゼロを選ぶと次の半バッファが実質停止し、PCMで2.95msの無音を検出したため。これは数msの位置誤差と引き換えに無音区間を避ける選択で、最終測定の誤差は最大2.45msだった。
4. 補間が済んでから通常トランスポートへ戻す。キー・ロックもこの時点で戻す。先に戻すとリサンプラー切替が最後の補間を飛ばすことを追加試験で確認し、修正した。

解放後に位置を止めて待つ段階も、着地シークもない。ただし速度を不連続に変えないため、通常速度までの短い補間区間は存在する。「離した瞬間から数学的に速度1.0」とは定義せず、コマンド受信から安定した通常速度への復帰を30ms未満とし、そこから1秒以上は1.0±0.1を検証する。補間中も音声を連続して生成する。

512フレームではコマンド受信〜コールバック待ちを含め30.79msになったため、出力を256フレーム / 44.1kHz（1バッファ5.805ms）へ変更した。位相補正をなくす設計変更と、30msの時間予算を満たすバッファ設定の両方が必要だった。

48kHz音源を44.1kHzで再生する場合、停止付近のリサンプラーの方向反転が振動を作った。512フレームで約1ms、256フレームで元のゲインのままだと約±10msになったことを実測した。上記のゲイン設計と、位置誤差1ms以内ではレートをゼロにすることで保持を無音にする。heartbeatは位置変更ではないため、停止後の減衰を解除しない。

曲変更・セッション変更・終了はabort。補正バッファを作らず解放する。通常のendは最後の受信位置を使用する。ホストと音声側の1500msウォッチドッグは維持する。

## 配置専用クオンタイズの契約

| 操作 | 挙動 |
| --- | --- |
| quantize ON/OFF | ホストの配置設定のみ変更。Mixxxのquantizeは常時0 |
| 現在位置へのHOT CUE登録 | ホストで可変ビートグリッドの最寄り拍を求めて明示位置で登録。個別の`quantize:false`も維持 |
| 明示位置のHOT CUE復元・登録 | 指定位置を保持 |
| ビートループ | グリッドから開始位置とN拍後の終了位置を計算。1拍未満は拍の分割位置へ丸める。ONにする操作なので、後にループ端へ到達すれば通常どおりループする |
| 明示ループ設定 | 指定区間を保存。設定操作で再生位置を移動しない |
| ビートジャンプ | Mixxxの`findNBeatsFromPosition`を使用する既存の明示ジャンプを維持。可変テンポと拍内オフセットを保持 |
| SYNC | テンポ同期のみ。quantize設定にかかわらず自動位相シーク・継続的な位相補正は行わない |

SYNCを押したときだけ位相シークを残す案は採らなかった。現在の要件は通常再生のタイミング維持を優先しており、明示的な位相合わせ専用操作を追加する依頼はないため。BPMの異なる曲のSYNCでは、テンポそのものは意図どおり変更される。

## リアルタイム処理と計測

アダプターのコールバックは固定長のatomicメールボックスを一度読み、整合しなければ前回値を再利用する。再試行ループ、ロック、動的確保、JSON生成は行わない。旧実装で整合性確認後に読んでいた終了方式フラグも、確認前のスナップショットへ含めた。

`scratch2`と`scratch2_enable`はこのホスト内部専用で、MixxxのRateControlが値を読むだけ。音声開始前にこの2つのControlDoublePrivateのQtシグナルを無効化し、コールバックでは`setAndConfirm()`を使用する。シグナル配送、ControlObject探索、振る舞いオブジェクト参照をコールバックから避ける。その他のMixxx内部処理は固定upstreamのまま。

`DJALY_MIXXX_TIMING_TRACE=1`の場合だけ、各デッキの8192行SPSCリングに時刻・位置・実速度・指定レート・目標位置・コマンド待ち時間を記録する。満杯なら待たずにドロップし、件数を返す。`deck.timing.trace`でQtスレッドから回収しJSON化する。テストはドロップ0を要求する。NaN番兵は使用していない。

`timing.test.mjs`は437.3HzのPCMとコールバック列を保存する。音声位置はバッファ終端、速度はそのバッファの実移動量。復帰時間は、以降1秒以上すべてのバッファが許容速度に入る区間の開始までをコマンド受信基準で計測する。位置誤差は解放目標から通常再生が進んだ分を差し引いて求める。

レート補間モデルからの残差も測る。Mixxxの方向反転時のサンプル履歴により約1msのモデル誤差があるため、スクラッチのモデル残差上限は2ms。定常再生・配置操作は1ms未満、実測ではほぼゼロ。PCMの隣接サンプル差と連続無音長も別に検査する。

最終ビルドの44.1kHz音源、44.1kHz / 256フレーム出力で、前後600〜900msを150msで動かし、入力間隔5・16・25ms、キー・ロックONを含む8ケース:

| 指標 | 実測 |
| --- | --- |
| コマンド受信〜安定した通常速度 | 12.03〜16.49ms |
| 解放位置の最大絶対誤差 | 1.973ms |
| 安定復帰後1秒以上の速度 | 1.000〜1.025（±0.1以内） |
| 代表解放区間のPCM隣接差 | 最大636 / 16bitスケール |
| 代表解放区間の連続無音 | 最大0.045ms（2サンプル、ギャップ基準2ms未満） |

| 停止中の配置操作後の位置誤差 | 0ms（丸め誤差のみ） |

証拠: `/var/folders/39/w3nmjg1566q3djxm89qhhvhc0000gn/T/djaly-timing-WlXpns/evidence.json` と同ディレクトリのWAV。テストの証拠ファイルは一時ディレクトリに残す。

最終ビルドで、指定の8実機テストファイル＋追加timingテスト（計11テスト）はすべて合格。`native/dj-engine-host/tests-node/*.test.ts`は72件合格。停止保持中と停止状態での解放後のPCM RMSはともに0。`pnpm dj-engine:stage`と署名・依存ライブラリ監査を実施済み。以前のステージは`stage/.staging.JUO3ct`に保存されている。

## 再実行

Djalyを終了してから実行する。複数ホストで同時にオーディオ計測しない。

```sh
cmake --build native/mixxx-engine-host/build-upstream --target djaly-mixxx-engine-host --parallel 6
cmake --build native/mixxx-engine-host/build-seam --parallel 6
node --test --test-concurrency=1 native/mixxx-engine-host/tests/{scratch,seek-drag,dj-controls,beatgrid,variable-beatgrid,protocol,first-fx,recording-finalization,timing}.test.mjs
DJALY_TIMING_SOURCE_RATE=48000 node --test native/mixxx-engine-host/tests/timing.test.mjs
node --test native/dj-engine-host/tests-node/*.test.ts
pnpm dj-engine:stage
```

測定対象は実際のMixxx音声処理・内部録音PCM。スピーカーまでのD/A・機器固有の遅延、ブラウザのpointerup発生からJSONが届くまでのOS/UI待ちはこの復帰時間に含めない。プリロールのJavaScriptタイマーを音声サンプル精度にする変更も含めていない。今回再現した正時間のドラッグ解放ではプリロール経路に入らない。
